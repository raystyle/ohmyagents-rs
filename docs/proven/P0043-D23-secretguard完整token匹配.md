# D23 secretguard 完整 token 匹配

- 状态：已完成（135 单元全绿；随 v0.4.0 发布）
- 日期：2026-09-10
- 关联：PRD D23；ohmyagents-rs#9；S030 八层防线；D20（providers 层已删）

## 背景与问题

ohmycloud 开发 omc 配置渲染代码时被 oma secretguard 连续误拦：实值比对是裸子串匹配，模型别名（如 deepseek 线别名）作为更长连字符标识符的真子串即触发 block。诉求三点：收窄误报、保留真实拦截、告警可定位。

## 方案

- `contains_complete_token`：值命中要求两侧无 [A-Za-z0-9_.-] 类字符（完整 token 形态）。连字符超集（`值-ext` / `pre-值`）不再触发；真实密钥完整值（引号 / 空格 / 行边界包裹）仍 block。
- masked 升级为 `名[头4字符…长度]`（如 `SECRET_KEY[zq9w…18]`）：可定位触发词不泄密。
- 根因层（providers.toml 值源）已随 D20 删除；v0.3.0 在位端仍踩，随 v0.4.0 更新消除。

## 落地与验收

- 单测：超集前后缀不拦、完整 token 拦、多次出现循环推进、masked 形状、env 通道真值仍 block 加变体不拦 [实证： 全绿]。
- #9 回执随 v0.4.0 发布回贴。

## 经验

- 实值检测的边界语义：密钥泄露的自然形态是完整 token（赋值、引号、命令行参数），子串形态（更长标识符内嵌）几乎总是误报；按自然形态收边界比维护豁免清单稳。
- 本仓自 dogfood 复现 #9：修 D23 时自己的 Edit 被在位 v0.3.0 hook 拦（注释里的真实别名撞 providers 值），绕法 = 注释改中性示例词，侧面证明该误报对配置开发是日常阻塞级。
