## 背景与问题

S016 吸收裁决表标了三个「后续切片」：`--json` 信封、`oma status` TTY 表格、`oma completions`；另有错误 CTA 规范入 R002 的落点。P0011 落地后 api 层与信封已存在，`--json` 从「要做的事」变成「接一根线」，四件一次收口。

## 方案

- `--json`：api 层新增共用 `envelope(command, root, result)`（HTTP 已有的信封构造上提，server.rs 改走同一份）；六会话命令（spawn/status/send/run/settle/cleanup）加 `--json`，`print_json` 出口：信封进 stdout，业务失败先吐信封再返回 Err（stderr 错误行加退出非 0）——机器读者拿信封，人类拿错误行。
- TTY 表格：`oma status` 在 stdout 是 TTY 时打手写对齐表（AGENT/PID/PROCESS/TERMINAL/HOOK，列宽取最大字符宽、两空格槽、横线分隔），非 TTY（管道与测试）保持 marker 行——测试契约零变动。
- completions：`clap_complete`（clap 官方生态，R005 无争议）进普通依赖（小而稳，不值得 feature 门），`oma completions <shell>` 直出 stdout。
- R002 输出规范节：marker 默认、TTY 表格人读面、`--json` 三传输同形、错误带下一步（现有错误文案已内嵌 CTA，如 `run `oma spawn` first`，规范成文）。

## 验收标准与结果

- 单测：信封构造（ok/error 二态、meta 字段）加表格渲染（列对齐两断言、缺字段占位）过。[实证]
- 集成：`status --json` 无 manifest 时 stdout 可解析为信封（ok:false、error 含 spawn、meta.command 对）且退出非 0；`completions bash/powershell` 出非空脚本且 bash 含 `_oma`。过。[实证]
- 活体：stub 项目 `spawn/status/cleanup --json` 三连全 ok:true；completions powershell 出脚本。过。[实证]
- 基线：63+2+10（无 feature）、66+2+10（server,mcp）全绿；既有 marker 测试零改动零失败（双读者契约成立的直接证据）。过。[实证]

## 实施过程与经验

- 信封上提是本次唯一的结构动作：server.rs 私有 `envelope` 升 `api::envelope`，两处测试跟着改——三传输同形从约定变成同一函数。
- 批量加 clap flag 用 Python 锚点脚本：第一版锚（project 字段注释）撞 16 处（trace 六个子命令同款注释），第二版先按结构体开 brace 定位再找最近 project——**锚点脚本先数命中数再动手**（`assert count == 6` 把误伤拦在写盘前）。
- `IsTerminal`（std 1.70+）够用，不需要 isatty crate——表格分支不可自动测（测试非 TTY 恒走 marker），渲染函数抽纯函数单测覆盖。
