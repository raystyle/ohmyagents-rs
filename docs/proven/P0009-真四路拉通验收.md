- 状态：已完成（2026-08-31：claude 路全通，其余三路保守拦截符合设计；spawn cwd 缺陷已修）
- 日期：2026-08-31
- 关联：前置 P0005（预留「四路真实 agent 的 POC 放在全绿之后」）到 P0008（stub 全链路）；研究 `S006/S007`（信任门与 yolo）、`S009`（状态分层，备屏 TUI 限制）、`S015`（hook 注册矩阵）；参考 `R007`

## 背景与问题

oma 十命令全部在 stub（pwsh 桩）上验收。本机四家 agent 已装齐（`oma agents`：claude 2.1.246、codex 0.149.1、grok 1.0.13、kimi 0.38.0），编排器必须在与真实 agent TUI 的交互上过一遍才算数：真进程名 locate、真启动时序、真信任门、真 hook 事件、真状态判定。

## 目标与非目标

- 目标：
  - 临时项目目录走真四路：`oma init --yolo --pretrust` → `oma spawn`（四路真 agent，不阻塞）→ `oma status`（locate 反查各家真进程名；1b/hook 态）→ `oma run`（分派一路或几路，观察状态迁移）→ `oma cleanup`
  - 记录真 agent 与桩的行为差异（启动时序、1b 分类在 TUI 备屏的表现、hook 事件是否落地、confirm 语义是否适用）
  - 发现的问题按循环自迭代回写（研究/参考/坑）
- 非目标：
  - 不追求四家全自动化无人工（首次信任框、登录态属环境问题，记录即可）
  - 不做 REPL/HTTP（另立方案）

## 方案

1. 环境：临时项目目录；`oma init --yolo --pretrust` 铺无阻塞与信任库（S006/S007）
2. spawn：`oma spawn --agents claude,codex,grok,kimi`（真 argv = 各家二进制无参数进 TUI）；不阻塞，随后轮询 status 等四路进程名就位（locate 出各家的 exe）
3. status 快照：每路 pid、进程名（期望 claude.exe/codex.exe/grok.exe/kimi.exe）、terminal 态（TUI 备屏预期 unknown 或 working）、hook 态（注册是否被加载、事件是否写 state 文件）
4. run：分派一条轻任务（如让 claude 回一个短句）到单路；观察 hook state 是否 working、任务文件是否落
5. cleanup 后目录清理；结论回写本方案经验节
6. 每步的失败不回滚已验部分，记录后继续（验收性探索）

## 风险与预案

- 真 agent 首启弹信任/登录：pretrust 先铺；仍弹则记录为环境事实
- TUI 备屏 snapshot 空：S009 已知，1b 判 unknown 即符合预期
- confirm 对 TUI 不可靠：改用 hook state 迁移作送达证据；confirm 只在层 2 沉默时省略
- 进程名与预期不符（如 wrapper）：locate 结果照实记录进 S014 口径

## 验收标准

- 四路真进程名 locate 正确、manifest 四路 pane id
- 至少一路真 agent 收到任务且状态发生可观察迁移（hook working 或任务文件落）
- cleanup 干净；差异与坑全部记录
- 文档同步与三件套过

## 实施过程与经验

### 全链路

> 2026-08-31 Windows 四路真 agent。

- **claude 路全通**（编排器对真 agent 可用的完整实证）：`oma init --pretrust`（全套 hook 部署加信任库）→ spawn 四路 → status locate 反查 `claude.exe` 正确 → `oma run` 过状态门（hook=idle）两段式发送 → 层 2 事件实时迁移 `SessionStart→idle`、`UserPromptSubmit→working`、`Stop→idle`，任务真被执行（TUI context 增长），`t001` 任务文件落。Claude 的 exec form hook 注册（oma.exe 加 args hook）实战可用。[实证: 全程标记行与 state 文件]
- **重大缺陷已修：spawn 未设 pane 进程 cwd**。daemon 由 WMI 拉起时 cwd 在 `C:\Windows\System32`，pane 进程继承——claude 在 System32 打开（信任框问的是 System32，误点后污染用户信任库，已清 `C:/Windows/System32` 条目，注意键为正斜杠形态）；hook 的 `project_allows` 因 cwd 不匹配项目而按设计静默（安全带正常工作，掩盖了根因）。修法：`ensure_session().working_directory(root)` 加 split builder `.cwd(root)`。修复后 claude 在项目目录直接进 REPL（pretrust 的 `hasTrustDialogAccepted` 对 claude 有效，无框）。[实证: 修复前后 capture-pane 对比] 坑记 M031。
- **codex/grok/kimi 三路保守拦截**（不误发，符合「仍 unknown 则不委派」）：hook 全 silent 加 1b 对 TUI 判 busy（光标不可见→Running→working）。三家沉默原因按 S015/S006 属信任流未走通：codex 项目 `hooks.json` 需 `hooks.state.trusted_hash` 信任确认；grok folder-trust 已写但 `.grok/hooks` 部署后仍需 `/hooks-trust` 类确认；kimi 项目级注册不存在且未写用户级。三家的信任流打通是后续工作，不是状态门的缺陷。[实证: run.skipped 各路 + state 目录无文件]
- **1b 分类器对真 TUI 的边界确认**：分类器为 shell 提示符设计（S010），真 agent TUI 光标隐藏即 Running、备屏空即 unknown——对真 agent 的权威必须靠层 2，层 2 沉默时状态门保守拦截正是设计意图。
- 环境：四家已装齐（claude 2.1.246、codex 0.149.1、grok 1.0.13、kimi 0.38.0）；claude 警告行显示继承宿主 `CLAUDE_CODE_*` 环境（spawn env 只增不洗，后续可评估白名单）。
- 过程小坑：`rg -rln` 替换标志第二次踩（M028 重犯，输出 `lnectory` 即污染征）——看输出出现无意义整词替换先查自己带的 `-r`。
