# S006-信任阻塞门-四家种类与官方口径

> 2026-08-31。由《信任阻塞种类-目录hook-skill-MCP》（2026-08-29，源码核实四家）与《Claude官方文档-阻塞门与编排对齐》（2026-08-29，官方文档订正 Claude 列）合并。Claude 列以 code.claude.com/docs 为权威，泄漏仓库 codeaashu/claude-code 降为历史对照；Codex / Grok / Kimi 仍以源码核实为准。本机 `claude 2.1.246` / `codex 0.149.1` / `grok 1.0.13` / `kimi 0.38.0`。

## 背景

编排器要在 spawn 前把会卡住 TUI pane 的信任门全部预写或检出。工具审批（yolo）不是 trust：trust 是「这段仓库代码能不能在你机器上跑」。本篇给四家门的种类总表、Claude 官方分路（交互对 `-p`）、以及 `init --pretrust` / `doctor` 的设置绕过检测口径。

## 关键结论

### 1. 四家门的种类总表

Claude 列按官方文档口径重写（旧泄漏口径的订正见第 4 节核查表）。[实证: 2026-08-29 官方 permissions/hooks/mcp/skills 分表；Codex/Grok/Kimi 源码核实]

| 种类 | Claude（官方口径） | Codex | Grok | Kimi |
| --- | --- | --- | --- | --- |
| 项目目录 | 键 `~/.claude.json` `projects.<abs>.hasTrustDialogAccepted`；父目录覆盖子目录；家目录只记会话；`-p` 关掉信任校验 | `[projects."<abs>"] trust_level=trusted`；未信任则整层项目 `.codex/` 不加载 | `~/.grok/trusted_folders.toml`；空仓不提示；无头有配置则静默 Untrusted | `~/.kimi-code/workspace-trust/wd_*`；默认 Don't trust |
| hook | **并入 folder**：交互下所有 settings hooks 卡到 folder 信任被接受；无独立 persist 键。`-p` 当 trusted 直接跑 | **独立**：`HookTrustStatus`=untrusted/trusted/modified；`[hooks.state.<源>] trusted_hash`；`--yolo` 不绕过 | **并入 folder**：`--trust` 一次授权 MCP+LSP+hooks 等 | 无独立框；hook 注册在用户 `config.toml` |
| skill | **普通 skill 非独立门**（`allowed-tools` 走权限流，trust 从不挡）；**skills-dir plugin 形态要 workspace trust** | 跟项目层：未信任则项目 skill 不加载 | **不在** folder-trust 触发种类里（种类含 mcp/plugins/lsp/envrc/hooks 等，无 skills） | 项目 `.kimi-code/skills` 无额外框 |
| MCP | **独立**：交互弹 per-server 审批；v2.1.196+ 仓库 committed 审批在未信任夹被忽略；`-p` 不问就连 | 依赖项目信任层 | 并入 folder（`.mcp.json` 等触发） | 未核到独立框 |
| YOLO 确认框 | `BypassPermissionsModeDialog` 写用户 settings `skipDangerousModePermissionPrompt`（scope：User/local/managed） | 沙箱审批是 yolo 不是 trust | always-approve 是权限不是 folder | `StartPermissionPrompt`（auto/yolo/manual）归 yolo 不归 trust |

### 2. Claude 官方把门拆开了：交互与 `-p` 不是同一套

官方 permissions.md「What runs before you trust a folder」按内容种类、按会话类型分表：[实证: 2026-08-29 对照官方分表]

- hooks、`env`、`apiKeyHelper`、skill 的 `allowed-tools`：两类会话都可用。
- `permissions.allow` / `additionalDirectories`：未信任时**不生效**（交互再弹框；`-p` 打 stderr）。
- `.mcp.json`：交互**会问**（仓库自己写的审批不算）；`-p` / SDK **不问就连**（还要 `settingSources` 含 project）。
- 项目 subagent frontmatter hooks、`@skills-dir` plugin：未信任**不用也不弹**。
- `-p` 无 `--bare` 时会跑未信任仓库的 hooks、连 `.mcp.json`；`--bare` 全跳（官方推荐脚本路线，将来变 `-p` 默认）。

TUI pane（交互）与脚本 `-p` 必须分路诊断：不能把「`-p` 不弹」理解成「交互也不弹」。

### 3. YOLO 语义（Claude）

本节断言来源：官方 permission-modes / settings-reference / headless 与 issue 10409，2026-08-29 核。[实证: 官方文档对照]

- 模式链 `default(Manual) / acceptEdits / plan / auto / dontAsk / bypassPermissions`；交互 Pro/Max 起点 v2.1.228 起是 auto，`-p` 起点仍是 Manual。
- **auto 不能从项目或 local settings 生效**（只用户 / managed）；仓库不能自授 auto。
- 本仓 YOLO = `bypassPermissions`：交互首次出责任框，接受写用户 settings `skipDangerousModePermissionPrompt`（只问一次）；`-p` 不弹此框；`--bg` 未曾在交互接受过则拒启。
- `--allow-dangerously-skip-permissions` 只把 bypass 加入 Shift+Tab 循环，不激活，也不管目录/MCP 框。
- deny 规则、ask 规则、`requiresUserInteraction` MCP、关键路径 `rm` 任何模式都不自动批。
- `--dangerously-skip-permissions` 跳过信任检查但**不写** `hasTrustDialogAccepted`（issue 10409）——不能用 YOLO flag 代替信任键。

### 4. 核查表（旧泄漏与源码主张对官方口径）

判定依据：官方文档对照（前两行与后三行）与源码核实（中间行）。[实证: 2026-08-29]

| 主张 | 结论 |
| --- | --- |
| `hasTrustDialogAccepted` 是 folder 落盘键 | 成立（官方明文） |
| 独立 `hasTrustDialogHooksAccepted` 是现役键 | 已过时：官方零记载；交互 hooks 跟 folder 走。双写无害但不构成检测依据 |
| committed `enableAllProjectMcpServers` 在未信任夹生效 | 不成立（v2.1.196+ 仓库不能自批自己）；生效来源：用户 / managed / `--settings` / 未跟踪 local（要等信任框） |
| 项目 `.claude/skills` 一律要 folder 信任 | 不成立：普通 skill 的 `allowed-tools` 不被挡；**skills-dir plugin 形态才要** |
| `-p` 等于 YOLO | 不成立：`-p` 起点 Manual |
| Grok always-approve 下 deny 与 PreToolUse hook 失效 | 不成立：仍生效（`现有研究复核` 独有增量，2026-08-29 官方文档） |
| Codex 用户层不加载 `~/.codex/hooks.json` | 不成立：官方列出 hooks.json 与 config.toml 都加载（同上来源） |

### 5. Grok / Codex / Kimi 源码核实要点

本节断言来源：`xai-org/grok-build` `folder_trust.rs`、`openai/codex` `hook_config.rs`、`MoonshotAI/kimi-code` 源码树，2026-08-29。[实证: 源码核实]

- **Grok**（`folder_trust.rs`）：一条 store 多种触发物；`GROK_FOLDER_TRUST=0` 或 `[folder_trust] enabled=false` 整门关掉；无头默认不提示、直接 Untrusted（静默跳过项目代码——看起来像「没 hook」，doctor 必须把「未信任 + 有 hooks」报 block）；over-broad 根（家目录）拒绝落盘直接当 trusted。
- **Codex**（`hook_config.rs`）：项目与 hook 两扇门正交；hook 命令变更会转 `modified` 再弹；bypass 用 `--dangerously-bypass-hook-trust`，`--yolo` 不绕过。
- **Kimi**：`StartPermissionPrompt` 是 permission mode 不是目录信任；源码树无对等的 folder+hooks 第二框。

### 6. 对本仓：设置 / 绕过 / 检测（交互 TUI pane 口径）

本节为前三节官方口径与源码结论落到 `oma init --yolo` / `oma doctor` 的推导；`trust.skill` 裁决与 poc-yolo-doctor 实测互证。[推断: 口径推导；实证: 2026-08-29 poc-yolo-doctor]

**设置**：folder 键写 `~/.claude.json`（Windows 路径拼写注意，见缺口）；YOLO 模式写项目 `.claude/settings.json` `permissions.defaultMode=bypassPermissions`；YOLO 确认写用户或 local 顶层 `skipDangerousModePermissionPrompt`（不进共享项目文件、不进 permissions 嵌套）；MCP 先 folder 信任再写 local `enableAllProjectMcpServers`；Codex 有项目 hook 时另写 `hooks.state.trusted_hash`；Grok `--trust` 等价写 store。

**绕过（按会话类型）**：交互 pane 全靠预写键；脚本 `-p` 默认不弹但 allow 规则仍不生效，免审批另加 `--permission-mode` / `--allowedTools`；不跑别人仓库 hooks 用 `--bare` 或 `--settings '{"disableAllHooks": true}'`。

**检测（doctor 拆类）**：

- `trust.project`：folder 键在不在（父路径覆盖）。
- `trust.hooks`：Claude 交互下 covered_by folder；Codex 看 `trusted_hash`；Grok 未信任 + 有 hooks 报 block（无头静默跳过）。
- `trust.mcp`：独立门。Claude 交互弹审批、committed 审批不算数；只写项目 settings 的 enable-all 不够。
- `trust.skill`：**只对 skills-dir plugin 形态报**（skill 目录带 `.claude-plugin/plugin.json`、`@skills-dir`、`extraKnownMarketplaces`）；普通 `.claude/skills` 不报，归 `trust.project`。这是 2026-08-31 的裁决：官方口径下普通 skill 非独立门，doctor 报宽了会把无需预写的项目标成 block。MISTAKES 同步订正。
- `yolo` / `skip_prompt` / `onboarding`：分立不绑 folder。
- 交互与 `-p` 的 block 语义相反（`-p` 跑未信任 hooks/MCP）；doctor 现按交互口径，加 `-p` 委派时要分路。

| 坑 | 正解 |

| 把 yolo 当 trust（或反之） | 两类门分开设、分开检 |

## 缺口

- `hasTrustDialogAccepted` 非可靠运行时信号；官方无 `claude trust status`。
- `onboarding` 键未在官方 settings 索引列出，写入时机未核。
- Kimi 项目 `config.toml` 是否加载 hook 仍未核。
- 未对本机四家做弹框时序录屏实证；与泄漏冲突处一律以官方为准。
- VS Code 扩展路径不覆盖（本仓 TUI pane 走 CLI）。
