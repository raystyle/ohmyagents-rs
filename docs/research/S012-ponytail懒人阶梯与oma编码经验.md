# S012-ponytail懒人阶梯与oma编码经验

> 2026-08-31。用户点名本仓缺一篇编码经验研究，参考 DietrichGebert/ponytail（MIT）的底层逻辑。来源为其 `skills/ponytail/SKILL.md`（main 分支，2026-08-31 web 读全文核实）。

## 背景

本仓已有写 Rust 规则（依赖怎么选）与测试标准细则（断言怎么写），缺一块：**实现怎么取舍**——写多少代码、在哪一层解决、什么不许省。ponytail 用「懒人阶梯」把这件事讲成可执行的反射。

## 关键结论

1. **懒是高效，不是粗心**：最好的代码是从没写过的代码。懒的解法 = 理解问题之后的最短工作路径，不是跳过理解的小 diff。[经验: ponytail]
2. **七档阶梯，在第一个撑住的横档停**：一，这需要存在吗（YAGNI，投机需求一句话跳过）；二，本仓已有就复用（最常见的 slop 是重复实现几个文件外就有的东西）；三，标准库能做就用；四，平台原生特性能覆盖就用原生（DB 约束优于应用代码）；五，已装依赖能解决就不加新依赖；六，能一行就一行；七，最后才是能工作的最少代码。[经验: ponytail]
3. **阶梯在理解之后跑**：先读任务涉及的每个文件、端到端追真实流，再爬阶梯。「省掉理解的懒」伪装成效率、发出自信的错误修复——最短路径的前提是改对地方。[经验: ponytail]
4. **bug 修根因不修症状**：动手前 grep 被改函数的所有调用方；共享函数里一个 guard 比每个调用方一个 guard 的 diff 更小，且只修工单点名路径会留下同样坏掉的兄弟路径——最懒的修法恰好就是根因修法。[经验: ponytail]
5. **无未请求的抽象**：单实现的接口、单产品的工厂、永不变化的值的 config、给「以后」搭的脚手架，都不要。删优于加、无聊优于聪明（聪明是别人凌晨三点要解码的东西）、最少文件、最短工作 diff。[经验: ponytail]
6. **刻意简化要留痕**：砍掉真实代价且已知天花板的简化（全局锁、O(n^2) 扫描、朴素启发式）加 `ponytail:` 式注释，写明天花板与升级路径。[经验: ponytail]
7. **不该懒的清单**：信任边界的输入校验、防数据丢失的错误处理、安全措施、明确要求的东西；用户坚持完整版就建，不重新争。对硬件留校准旋钮。非平凡逻辑（分支、循环、解析器、钱与安全路径）留一个最小可跑检查，平凡一行不需要测试——YAGNI 同样适用于测试。[经验: ponytail]
8. **与本仓已有规则同源**：AGENTS 写 Rust 规则「最流行最稳的库 + 最少代码接上 + 优先组合」就是阶梯第三到五档；「一次不拉一堆用不上的依赖」是第五档的反面禁令；测试细则「断言质量优先于数量」「慢测分离」与第七条同向。[推断: 对照两文]
9. **本仓已实证过阶梯**：paste POC 在 SDK `cmd()` 坏掉后没有自写协议帧，退到现成 CLI（第五档逆向运用——撤掉坏依赖层，用平台已有命令面）；`rmuxpoc` 收敛 `interactive_shell_argv` / `keep_alive_echo` 等供六个 example 复用（第二档）。[实证: 2026-08-31 examples 六件复用与 poc-paste 路线切换]
10. **对 AI 协作仓的适配**：ponytail 的输出纪律（代码优先、至多三行说明「跳过了什么、何时加」）与本仓对话效率一致；其「复杂请求先发懒版并同轮质疑需求」适合委派与 POC 切片节奏——一次一件，绿了再进。[推断: 对照本仓 PLAN 一次一件原则]

## 现状或实测

### ponytail 阶梯与 oma 场景对照

| 阶梯档 | ponytail 原文口径 | oma 对应 |
| --- | --- | --- |
| 1 不需要存在 | 投机需求跳过并一句话说明 | 未立项的需求不预写代码；测试细则「rstest 等设触发条件不预先引入」 |
| 2 仓里已有 | 找到就复用，别重复实现 | `rmuxpoc` 共用层；helper 收敛（测试细则命名节） |
| 3 标准库 | std 优先 | `std::process::Command` 起 CLI 而非引 runner crate |
| 4 平台原生 | 原生特性优于自建 | rmux CLI 面即「平台」：paste-buffer 等现成命令不自写协议 |
| 5 已装依赖 | 不为几行加新库 | AGENTS 写 Rust 规则最少依赖；SDK 坏层撤掉用 CLI 是同档修正 |
| 6 一行 | 能一行就一行 | POC 输出行式 `poc.x=y` 而非结构化日志框架 |
| 7 最少代码 | 理解后的最短工作 diff | example 每件只证一个部件；`Result<String>` 直达不引错误框架 |

### 与既有规则的三处分岔

1. ponytail 说「非平凡逻辑留一个 assert 自检即可」；本仓测试细则要求更严（正负例成对、期望值独立来源）——本仓取测试细则，POC 阶段以退出码与标记行充当该自检。[推断: 本仓阶段裁剪]
2. ponytail 的强度分级（lite/full/ultra）是会话开关；本仓不需要分级——规则常开，靠「不该懒清单」划界。[推断]
3. `ponytail:` 注释前缀：本仓尚无此约定。候选做法是「简化注记」——刻意砍掉的实现写清天花板与升级路径，防后人误当完整实现。是否引入待定。[假设: 引入后可降低误读，未验证]

## 踩坑沉淀

| 本仓坑 | 阶梯视角的教训 |
| --- | --- |
| SDK `cmd()` 注入 `-S` 在 Windows 必败 | 第五档反例：依赖层坏了不是绕着修补，是整层撤掉换平台已有面（全 CLI） |
| `start-server` 起 daemon 立即退（exit-empty） | 第三档前置没做：先用现成语义（tmux 兼容面）核对行为，再写启动逻辑 |
| 首版 poc-paste 在 example 里复制 payload 构造 | 第二档：写第二遍时收敛成 `payload_line()` |
| WMI 启动器想提前提炼进 `rmuxpoc` | 第七档纪律：先在 example 内私有跑绿，出现第二个使用方再上移 |
