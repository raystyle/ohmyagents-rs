# 现有研究复核与扩展

> 2026-08-29。用公开文档、GitHub、X 复核本仓 `docs/research/` 六篇对照，并补官方口径。不覆盖原文，本文件是沉淀报告。

## 需求

- 研究：现有六篇（控制面、drive、项目级 hook/skill、状态通道、跨平台、yolo 与无阻塞）哪些结论还能用、哪些要改、编排器实现应补什么。
- 核查：
  1. `skipDangerousModePermissionPrompt` 是顶层键还是 `permissions` 内；能否写进共享项目 `.claude/settings.json`。
  2. `--allow-dangerously-skip-permissions` 能否单独去掉 bypass 确认框。
  3. Codex 用户层 hook 是否加载 `~/.codex/hooks.json`。
  4. Grok 的 `[ui] permission_mode` 能否写在项目 `.grok/config.toml`。
  5. Kimi 项目目录 `config.toml` 是否加载 hook。
  6. rmux 是否提供 `paste-buffer -p` 与 `send-keys -H`；SDK 是否一等封装。
  7. rmux 当前发布版本。

意图：混合（复核 + 扩展）。锚点：本仓研究文、ohmypwsh 0017、`raystyle/evo-harness#2`、Anthropic / OpenAI / x.ai / Moonshot 文档、`Helvesec/rmux`。

## 结论

### 1. 产品形状（对照《四路会话的控制面与观察面》）

现役定位已是「通用多 Agents 自动配置和任务编排器」。那篇研究仍适合当**首期切面**：CLI 控制、网页只观察、默认四家。[推断: 对照三份 demo 与方案 0004] 不要把 demo-orchestration 的「Claude 当编排器」当目标；不要抄 broadcast-demo 的卡片 UI 和自包 paste。

web-claude-demo 的 PTY 字节流镜像、broadcast 的 split/spawn、orchestration 的专用 socket，作为手段仍然成立。evo-harness 的两平面（控制 vs 观察）对得上本仓 CLI / 可选网页。

### 2. Drive（对照《drive铁律与三段式粘贴》）

结论维持：文本与 Enter 分发；禁止对 Codex 发 `C-c`；禁止发送侧自包 `\x1b[200~`。[经验: win-rmux 2026-08-21 + evo-harness drive；实证补强见 2026-08-29 poc-drive]

扩展：`Helvesec/rmux` CLI 有 `paste-buffer`（man、dispatch、`buffer_parse.rs`；默认 choose-buffer 模板是 `paste-buffer -p -b`）。公开 `rmux-sdk` 的 `PaneKeyboard` 只有 `type_text` / `press`，`Pane` 有 `send_text` / `send_key`，没有一等 `paste-buffer`。实现应 CLI 逃生舱走 `load-buffer` + `paste-buffer -p`，与 evo-harness `driver.py` 一致。

`send-keys -H`：本轮 GitHub code search 未打到稳定命中。evo-harness 已写「老 daemon 无 `-H` 退 `Enter` 键名」。实现按该回退，装上 rmux 后再 `rmux send-keys --help` 核一次。

rmux 最新 GitHub release：`v0.10.0`（2026-08-04）。本机 PATH 仍无 rmux。

### 3. 项目级 hook 与 skill（对照《项目级hook与skill》）

大方向成立：编排钉在启动目录；信任库可以在用户家预写。

复核后的落点：

| 家 | 项目级能写什么 | 官方限制 |
| --- | --- | --- |
| Claude | `.claude/settings.json` 可写 hooks、`permissions.defaultMode`（Any file） | `skipDangerousModePermissionPrompt` **不能**写共享项目文件；范围是 User / Local / Managed。仓库不能替你跳过确认框。项目私有可用 `.claude/settings.local.json`（git 忽略）。 |
| Codex | `.codex/config.toml` 与 `.codex/hooks.json`，须先信任项目 | 未信任则跳过整个项目 `.codex/` 层。用户层官方列出 `~/.codex/hooks.json` **和** `config.toml` 都会加载。evo-harness「hooks.json 不是用户加载点」相对当前 OpenAI 文档**不成立**。 |
| Grok | 项目 `.grok/hooks/*.json`（要 folder trust）；skill `.grok/skills/` | `[ui] permission_mode` 官方写明默认只在用户 `~/.grok/config.toml` 或托管配置，**不是**项目 `.grok/config.toml`。仍读 `~/.claude/settings.json` 的 hooks。 |
| Kimi | skill：`.kimi-code/skills/` 与 `.agents/skills/` | hook 官方示例仍是 `~/.kimi-code/config.toml`。项目 `config.toml` 是否加载 hook：**仍未核实**。hook 进程 cwd 是会话项目目录，脚本可以放项目里、注册留用户配置。 |

「别人逃到用户级」的原因仍成立：项目 hook 命令一变就弹信任框。应对是预写信任 + yolo 持久化，不是把状态 hook 写进家目录当默认。

### 4. yolo 与无阻塞（对照《yolo与无阻塞启动-参数或配置》）

ohmypwsh 0017 与 `evo-harness#2`（OPEN）方向对：信任类不要每次 flags。

必须改正的细节：

- `skipDangerousModePermissionPrompt` 是 settings **顶层**布尔，不是 `permissions` 里的键。ohmypwsh `set-wsl-agent-config.ps1` 把它塞进 `permissions` 对象，与官方参考和 issue #65848 观察到的落盘形状（顶层键）不一致。`init` / `doctor` 应按顶层键读写。
- 该键范围是 User、Local、Managed。写进共享 `.claude/settings.json` 官方明确「不受信任的仓库不能替你跳过对话框」。项目级无阻塞应写 `.claude/settings.local.json` 或用户 `~/.claude/settings.json`，并继续预写 `~/.claude.json` 的 `hasTrustDialog*`。
- `--allow-dangerously-skip-permissions` 只是把 bypass 加进 Shift+Tab 循环，**并不**启动即 bypass，也**不能**单独关掉确认框。启动即 yolo 用 `--permission-mode bypassPermissions` 或 `--dangerously-skip-permissions`，再加顶层 skip 键。
- `--dangerously-skip-permissions` 仍会出确认框，除非 skip 键已持久化（issue #25503）。非交互 `-p` 不出该框，但后台 `--bg` 在交互里接受过之前会被拒绝。
- Grok always-approve：官方 `permission_mode` 默认只在用户配置。编排器应写 `~/.grok/config.toml` 的 `[ui]` 或启动带 `--always-approve`；不要假设项目 `.grok/config.toml` 能设默认模式。folder trust 仍用 `trusted_folders.toml` / `--trust`。
- Grok 在 always-approve 下 deny 规则和 PreToolUse hook 仍然生效。编排器的 secret-guard 类 hook 在 yolo 里仍有用。
- Codex `approval_policy=never` + `sandbox_mode=danger-full-access` 可进项目 `.codex/config.toml`，但项目必须先被信任，否则整层被跳过。

`doctor` 无阻塞诊断（只读文件、不 attach）方向正确，应核对：顶层 skip 键、Codex `[projects]` 信任、Grok `trusted_folders.toml`、Kimi workspace-trust、任务到 agent 的 JSON。

### 5. 状态通道（对照《agent状态通道》《rmux状态判断与hook补充》）

维持：不引入 herdr 运行时；语义用 idle/working/blocked；权威用项目内 JSON。

扩展：rmux 0.10 的 `Quiet`、`foreground_state`、`state_events` 都不分类 agent。`Quiet` 官方定义为快照稳定、不推断提示符。Drive 同步用层 1（wait-pane），委派和 doctor 用层 2（hook）。Notification 不要映成 idle。详见《rmux状态判断与hook补充》。

Codex `Stop` hook 不可靠：本轮未重新实测，仍以 win-rmux / evo-harness 注释为准，judge 不能只信 hook。

### 6. 跨平台（对照《跨平台与无浏览器》）

维持：Windows named pipe、POSIX unix socket、默认不弹浏览器、`--no-web`。rmux 官方宣称 Linux / macOS / Windows 原生，安装脚本 `irm https://rmux.io/install.ps1`。本机仍未装，Windows Job Object `os error 5` 仍待实测。

### 7. 扩展：委派前检查清单

实现 `init` / `spawn` / `run` 时按这次复核：

1. 配置优先、flags 单次覆盖（对齐 0017 与 `#2`）。
2. Claude skip 键写 User 或 Local，不写共享项目 settings。
3. Codex 先预写 `[projects."<abs>"] trust_level`，再写项目 hook。
4. Grok 权限模式写用户 config 或 argv；项目只放 hooks/skills/deny 规则。
5. Kimi hook 注册暂走用户 `config.toml`，脚本放项目、无 `OHMYAGENTS_*` 则 exit 0。
6. Drive 用 `paste-buffer -p`，不要 SDK 自包 bracketed paste。
7. spawn 立即返回；`doctor`/`status` 看任务指向。
8. 不要把 `wait-pane --quiet` 当 agent idle；忙闲只信 hook 文件，存活只信 pane/pid。

## 缺口

- **Kimi 项目 `config.toml` hook**：官方页仍只写用户文件。本轮未读 kimi-code 源码加载器。
- **`send-keys -H`**：rmux 公开搜索未确认；实现保留 evo-harness 回退。
- **Grok 项目 config 里的 permission_mode**：permissions.md 与部分 user-guide 示例冲突；未跑 grok 实测。
- **本机 rmux**：未安装，pipe、Job Object、paste-buffer 行为未在本机跑过。
- **Codex Stop hook**：未对本机 0.149.1 复测。
- **X 上 rmux 编排讨论**：关键词噪声大，对本仓决策无额外工程信息。
- **Claude `permissions.defaultMode=bypassPermissions` 写在共享项目文件**：官方允许 Any file，但 auto 模式从项目文件会被忽略；bypass 在项目文件是否始终生效，本轮未单独实测。

## 对六篇原文的处置

原文保留当专题。本报告改口径处，实现以本文件为准：

- yolo 文：skip 键改顶层、改 Local/User 范围；Grok 权限模式改用户 config；补 `--allow-` 与 `--dangerously-skip-` 区别。
- hook 文：Codex 用户层包含 `hooks.json`；Kimi 注册暂留用户配置。
- drive 文：paste-buffer 走 CLI；SDK 不充当 paste API。
