# S019：四家会话日志格式与联邦检索取证

- 日期：2026-08-31
- 关联：方案 `P0013`（联邦检索）；前置 `S018`（aitrace 机制）；用户定调「反正各 agent 的源代码和文档都要核实研究」
- 研究法：**本地实证先行**（四家都在本机真实跑过，直接采样原生会话库）+ **源码核实跟进**（grok-build 与 kimi-code、codex 三仓浅克隆，两路子代理深读，载荷性断言回源码抽查）；时间戳/键位等细节以本机实物为准

## 一、为什么研究

P0013 定案查询时联邦架构：oma 在查询时直接读四家原生会话库并归一化。前提是四家库各自携带**项目归属、工具调用身份、双意图、编辑内容**四要素。本研究把这四要素逐家钉死（本地实证 + 源码保证），并纠掉三处想当然。

## 三、源码核实的三处纠偏

> 子代理深读三仓源码后的关键订正，全部有行号证据。[实证: 源码]

1. **grok-build 是 Rust 不是 TypeScript**：workspace `crates\codegen\*`（xai-grok-shell 等）。认知纠偏，无实现影响。
2. **grok `chat_history.jsonl` 是派生缓存不是权威**：grok 仓内官方文档（`xai-grok-pager` 的 user-guide 17-sessions 篇）明确 `updates.jsonl` 才是权威会话日志，chat_history 会被整体重建（`rebuild_chat_history`，compaction/rewind 触发）。oma v1 读 chat_history（本机实证其形状稳定），**升级路径是 updates.jsonl**（信封形 `{timestamp,method,params}`，需另行归纳 method 分类学）。grok 的 `backend_tool_call` 只覆盖服务端三工具（web_search/x_search/code_interpreter），**文件编辑在 `assistant.tool_calls[]`**——两处都想当然过，源码纠正。
3. **kimi `agentId` 是版本分水岭不是 schema 缺失**：旧会话（≤2026-08-19）wire 记录无顶层 `agentId`，新会话有（HEAD `serialize()` 复制全部自有键）。oma 解析按可选字段处理，agent 归属兜底目录路径 `agents/<id>/`（编址规则恒定）。

## 四、codex 源码核实的增量发现

- **`FileChange` 是编辑的权威结构化记录**（`event_msg/item_completed`，`item.type=="FileChange"`）：`changes: {绝对路径 → add{content}|delete{content}|update{unified_diff,move_path}}`、`id=call_id`、`started/completed_at_ms`、`turn_id`。生成点唯一（apply_patch handler），且 **shell 拦截路径**（`exec_command` 里 `apply_patch <<EOF`、`pwsh -Command` 等）同样产生 FileChange——oma 由此漏不掉 shell 形式的补丁。shell 里 sed/PowerShell 写文件只有 `CommandExecution` item（无 diff），是启发式痕迹不是权威编辑。[实证: 本机 hyper-v-lab 会话采样 + 源码 handlers]
- **排序用 `ordinal` 不用行 timestamp**：新会话 deferred creation，首批行批量落盘导致行时间戳偏移（实测首行外层时间比文件名晚 42s）。[实证]
- **cwd 语义**：`session_meta.cwd` 启动定死不随 cd；每 turn 另有 `turn_context.cwd`。补丁路径「绝对直用、相对拼 turn cwd」。[实证: 源码 config/recorder]
- 注入上下文过滤清单：codex 自带 `CONTEXTUAL_USER_FRAGMENT_MATCHERS`（`# AGENTS.md`、`<environment_context>`、`<turn_aborted>`、`<user_shell_command>`、`<subagent_notification>`、`<current_time_reminder>` 等）——oma 的过滤清单对齐其主要项。
- **append-only 成立**（唯一打开方式 append；compaction 是追加 `Compacted` 行不改写）；resume/fork 建新文件 `_<rollout_id>` 后缀；冷文件会被压成 `.jsonl.zst`（读侧透明）；`archived_sessions\` 归档目录——扫描要容忍。[实证: 源码 + 本机 0.149.1 与 HEAD 一致性比对]
- **rollout 无官方文档**：源码是唯一事实源；hook payload 含 `transcript_path`（即 rollout 路径）可做将来的实时关联。
- 版本容错：0.149.1 事件名 `task_started/task_complete`，HEAD 已改 `turn_started/turn_complete`；行类型全集比观测多五种（inter_agent_communication 等）——解析必须容错未知 type。

## 五、kimi 源码核实的增量发现

- `session_index.jsonl` 是 append-only 带墓碑（`{sessionId, deleted:true}` 行无 workDir）——**删除标记必须先于项目过滤判断**（本日实踩：墓碑行被 workDir 前置过滤跳过）。[实证: 源码 sessionLifecycleService + 失败测试]
- `wd_<slug>_<hash>` 用 v2 算法（反斜杠转正斜杠、basename slugify、sha256 前 12 字符）；v1 用 `pathe.resolve` 结果不同，不要用。
- 意图源分层：`turn.prompt` 的 `origin.kind` 是判别联合（user/skill_activation/injection/shell_command/system_trigger/cron_job/hook_result 等 12 种）——**只有 `user` 是真实用户意图**，对应 grok 的 `synthetic_reason` 过滤。assistant 文本权威源是 `context.append_message`（`content.part` 是流式碎片含 think 中间态）。
- 关联三键：`tool.call.uuid ↔ tool.result.parentUuid` 直连；`stepUuid` 聚 step；同 step 内 assistant part 先于 tool.call 落盘（`loopService.ts:863-864` 顺序保证）。
- 会话 uuid 是 **v4 无时间序**（与 grok v7 相反）——排序一律靠显式时间戳。
- 媒体 part 落盘被替换为 `{type:'blob_ref'}`——文本检索跳过。

## 六、grok 补充

- 目录名编码：`urlencoding::encode(cwd)`（超长回退 `{slug}-{blake3}` + 目录内 `.cwd` 文件）；解码优先 URL 解码失败读 `.cwd`。
- `prompt_history.jsonl` 是按 cwd 共享的输入侧索引（上限 1 万条、原子截断），**不是意图权威源**（与会话日志无因果定位）。
- `reasoning.summary` 可读、`encrypted_content` 是加密透传 blob 不可检索。
- 本地实证的编辑意图样例：`<user_query>` 标签内嵌在 user content 里（真实数据可见），oma 原样透传。

## 七、关键结论

1. 联邦架构成立：四要素四家全有，且都有源码级保证。[实证]
2. 时间统一必须做 epoch ms 归一（claude/codex ISO、kimi 原生 ms、grok uuidv7 近似）——跨家排序才能正确；ISO↔ms 互转用 Howard Hinnant 算法自带（免引 chrono）。[推断→实证: timeline 排序修复]
3. 每家的「注入过滤」形状不同但同构：claude isMeta、codex 注入 marker 清单、grok synthetic_reason、kimi origin.kind——**这是用户意图不被污染的四把闸门**，各 loader 必须自带。[实证]
4. grok 的 v1 局限（chat_history 派生缓存、行无时间戳用 uuidv7 会话起点近似、kind 无 create/delete 信息）与升级路径（updates.jsonl）已文档化，检索可用性优先。[推断: 取舍裁决]
5. oma 的 loader 全部「读时容错」：坏行跳过、未知 type 忽略、字段缺失置 None——append-only 尾部截断与版本漂移不崩检索。[经验: S018 同姿态]
